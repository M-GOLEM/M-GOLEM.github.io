Building a TOTP vault in .NET: AES-GCM, PBKDF2 and the limits

.NET · 17 Nov 2026 · 9 min read

TOTP looks like magic: a six-digit code that changes every 30 seconds, derived from a shared secret and the clock. The algorithm is small. The hard part is storing the secret without weakening it.

1. The code is an HMAC

RFC 6238 builds on RFC 4226 (HOTP). With a base32-decoded secret K and time step T = floor(unixSeconds / 30):

H = HMAC-SHA1(K, T as 8-byte big-endian)
offset = H[19] & 0x0F
code = ((H[offset] & 0x7F) << 24
      | H[offset+1] << 16
      | H[offset+2] << 8
      | H[offset+3]) % 1_000_000

Pad to six digits. SHA-1 is not a weakness here — HMAC-SHA1 remains fine for this construction — but many servers now accept SHA-256 or SHA-512 and 8 digits.

Two practical details:

  • Clock skew. Servers usually accept the previous, current and next window. A device more than ~30 seconds off will fail.
  • Replay. A code is valid for the whole window. The server must remember used codes if replay matters.

2. Storing the secret

A TOTP seed is as sensitive as a password that never expires. Encrypt the whole vault, not individual fields:

  • KDF: PBKDF2-HMAC-SHA512 with a random 32-byte salt and a high iteration count (300,000 is a reasonable 2026 baseline). Argon2id is better if the platform allows it.
  • Cipher: AES-256-GCM, a fresh 12-byte nonce per save, and the 16-byte tag stored with the ciphertext.
  • Layout: salt ‖ nonce ‖ tag ‖ ciphertext. Version it so you can migrate later.
  • Writes: write to a temp file, flush, then replace. A half-written vault is a lost vault.

Do not invent your own construction, and do not use AES-CBC without a MAC.

3. Where designs fail

The PIN check is part of the crypto

A common mistake is to verify the PIN against a hash constant compiled into the application, then derive the vault key from whatever the user typed. If the constant is the real gate, the key derivation adds nothing: anyone with the source knows which PIN opens the vault.

Fix: derive a verification key from the password with the same KDF, store only an HMAC of a fixed string under that key, and use a separate derived key for encryption. The password never exists as a constant, and changing it means re-encrypting, not editing source.

Comparing secrets with ==

String equality exits early. Use a fixed-time comparison for tags and verifiers. In .NET, CryptographicOperations.FixedTimeEquals.

No backup, no recovery

If the vault file and the password are both required and neither has a backup path, one disk failure locks the user out of every account. Offer an encrypted export, and tell users to store provider recovery codes separately.

Secrets in memory forever

Once decrypted, seeds live in managed strings that the GC may copy. You can reduce exposure with byte[], CryptographicOperations.ZeroMemory and short unlock sessions, but you cannot fully defend against a process with debug rights. Be honest about that in the threat model.

4. What TOTP does not stop

  • Real-time phishing. A proxy can ask for the code and use it immediately. Passkeys/WebAuthn are the answer; TOTP is not.
  • Malware on the unlocked machine. If the vault is open, the seeds are readable.
  • Account recovery attacks. The weakest link is often the email or SMS fallback, not the code.

For high-value accounts, use a hardware security key. TOTP is a solid second factor, not a substitute for one.

5. A sane checklist

  1. Base32 decode strictly; reject bad padding and non-alphabet characters.
  2. PBKDF2/Argon2id with a random salt, stored with the ciphertext.
  3. AES-GCM with a unique nonce per encryption.
  4. Fixed-time comparisons for tags and PIN verifiers.
  5. Atomic writes and a documented backup/export path.
  6. A written threat model that admits memory scraping and phishing.
