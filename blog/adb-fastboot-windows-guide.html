ADB and fastboot on Windows: a diagnostic guide

Android · 17 Nov 2026 · 9 min read

Most "my tablet is dead" cases are a cable, a driver or an authorisation prompt — not a broken device. ADB answers the question "is the software alive?" before anyone reaches for a firmware package.

Everything below is read-only diagnostics on a device you own. Nothing here flashes, unlocks or wipes anything.

1. Install only platform-tools

You do not need Android Studio. Download Google's platform-tools zip, extract it to a fixed path such as C:\platform-tools, and add that folder to PATH. Verify:

adb version
fastboot --version

On Windows, use a data-capable USB cable and a rear-panel port on a desktop. Front-panel ports and charge-only cables cause more "device not found" reports than any driver issue.

2. Authorise the connection

adb devices -l

The four states mean different things:

  • device — authorised and ready.
  • unauthorized — accept the RSA fingerprint prompt on the device. If the prompt does not appear, revoke USB debugging authorisations in Developer options and reconnect.
  • offline — usually a stale server. adb kill-server, then adb start-server.
  • empty list — cable, port, driver or "USB debugging" is off.

3. Read the device before touching it

adb shell getprop ro.product.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.fingerprint
adb shell dumpsys battery
adb shell wm size
adb shell wm density
adb shell df -h /data

These five minutes of output tell you the model, firmware build, battery health, display configuration and free space. That is the difference between "it boots to a logo" and a useful bug report.

Third-party packages and logs

adb shell pm list packages -3
adb logcat -d -v time *:E

Filter logcat by PID or tag once you know which app crashes. A full unfiltered dump is noise; an error-level dump around the failure is evidence.

4. Capture what the screen shows

adb exec-out screencap -p > screen.png
adb shell screenrecord --time-limit 20 /sdcard/demo.mp4
adb pull /sdcard/demo.mp4

A screenshot of the recovery or error screen is often more useful than a description, and it survives the device being wiped later.

5. Know which mode you are actually in

"Fastboot" is not a universal rescue mode. The connection mode determines which tool can talk to the device at all:

  • ADB — Android is booted; debugging is on.
  • fastboot — bootloader is up; fastboot devices should list it. getvar all is safe and informative: fastboot getvar all.
  • Samsung download mode — Odin/Heimdall territory, not fastboot.
  • Qualcomm EDL (9008) — a serial download mode; tools and firehose loaders are per-OEM. Treat it as a last resort; one wrong load can brick a device.
  • MediaTek preloader / BROM — another vendor-specific path.
  • Spreadtrum — its own download tool.

6. Drivers: identify, do not guess

Open Device Manager and look at the VID/PID and the device class. A yellow mark on "Android" or "Unknown device" means the mode is not bound to a driver. Google's USB driver covers Nexus/Pixel; Samsung, Qualcomm and MediaTek modes need their own vendor drivers. Installing a random "universal ADB driver" pack is a good way to break a working setup.

7. What not to do

  • Do not flash a firmware package you cannot verify against the model and region. Cross-flashing is how devices lose their IMEI or boot loop.
  • Do not run EDL/firehose packages from unknown sources.
  • Do not lock the bootloader on a device with a custom image unless you have read the vendor's exact procedure.
  • Do not use these steps on a device you do not own.
