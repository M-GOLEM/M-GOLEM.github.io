DNS ad blocking on Android without root

Android · 17 Nov 2026 · 7 min read

Most mobile ads start with a DNS lookup. Block the lookup and the ad never loads — no root, no browser extension, and it works inside apps.

Android exposes this through VpnService. The name is misleading: the app does not need a remote VPN server, and it does not need to see your traffic. It can capture DNS and leave everything else alone.

The packet path

  1. The app calls VpnService.Builder and adds a DNS server address that points back into its own tunnel.
  2. Android creates a tun interface. The app reads raw IP packets from it.
  3. For each UDP packet to port 53, the app parses the DNS header and question name.
  4. The name, and its parent domains, are checked against the blocklist.
  5. Blocked: the app writes an NXDOMAIN response back into the tunnel. Allowed: it forwards the query to a real resolver and copies the answer back.

No root, no iptables, and no traffic leaves through a third-party server. The app is a DNS proxy, not a tunnel for your browsing.

Making lookups fast

A hosts-style list with a few hundred thousand entries is too slow to scan per query. Two changes make it practical:

  • Store each domain as a 64-bit hash in a sorted array and use binary search — memory stays small and lookup is O(log n).
  • Cache the compiled array on disk, so only the first start pays the parse cost.

Hashing also avoids keeping a readable list of every blocked domain in memory, which is a small privacy win. Collisions are possible in theory; with 64 bits and a few hundred thousand entries they are negligible for this use.

Choosing lists

More lists is not always better. A balanced set blocks ad and tracker domains without breaking logins, payments or app updates. An "ultimate" set will block more ads and also more legitimate first-party endpoints. The right level depends on how much breakage you tolerate.

The four cases where DNS filtering loses

1. DNS-over-HTTPS / Private DNS

If the app or the OS resolves names over HTTPS, the query never reaches your port-53 listener. On Android 9+, Private DNS must be off (or set to "Automatic") for system-wide filtering. Browsers with their own secure DNS need the same setting disabled.

2. Same-domain ads

When the ad is served from the same host as the content — some video and feed ads — blocking the domain blocks the content too. DNS cannot separate them.

3. One VPN at a time

Android allows a single active VPN. A corporate or privacy VPN will conflict with the blocker; only one can run.

4. Hard-coded IPs

An SDK that talks straight to an IP address bypasses DNS entirely. That is rare for ads, common for telemetry.

Privacy trade-offs

A DNS blocker sees every domain you resolve. That is a real position of trust. Good implementations keep the data local, publish no analytics, and let you pick the upstream resolver. Note that the upstream resolver — Cloudflare, Google, your ISP — still sees allowed queries. Moving DNS does not make you anonymous.

Practical setup

  1. Install the blocker and grant the VPN permission. The OS warning is expected; check that the app routes only DNS.
  2. Disable Private DNS while the blocker is active.
  3. Exclude the app from battery optimisation if protection dies after reboot.
  4. Start on a balanced list; move to a stronger one only if you accept breakage.
  5. Keep one browser without the blocker for banking or logins that misbehave, so you can tell "site is down" from "my filter broke it".
Tooling note. Ad-Blocker implements this model in Kotlin: a local VpnService, IPv4/UDP DNS parsing, hashed blocklists with binary search, three list levels and on-device statistics.
